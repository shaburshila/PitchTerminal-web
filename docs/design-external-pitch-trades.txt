DESIGN DOC — Indexing external PITCH trades for money-weighted portfolio ROI
PitchTerminal-web  |  read-only research + design  |  2026-05-31
================================================================================

PURPOSE
-------
The portfolio ROI on /api/v1/profile is being redefined to a MONEY-WEIGHTED
basis that accounts for the *real cash* a wallet put into / took out of the
PITCH ecosystem through external DEX trades (PITCH <-> ETH/WETH/USDC), denominated
in PITCH:

    ROI = (current_holdings_value_pitch + external_pitch_out - external_pitch_in)
          / external_pitch_in

We need, PER WALLET, two new aggregates:

    external_pitch_in  = PITCH acquired by SPENDING ETH/WETH/USDC on a DEX
    external_pitch_out = PITCH DISPOSED for ETH/WETH/USDC on a DEX

These MUST exclude:
  * in-app PITCH<->country/player bonding-curve trades (already in `events`)
  * pack-opening (PITCH spent, no token returned)
  * plain transfers / airdrops / referral payouts (no swap)

`current_holdings_value_pitch` already exists: it is summary.totalValuePitch in
profile.py (computed from on-chain balanceOf * market_state price_pitch).

PART B — CLASSIFICATION RULE (robust, tx-level)
================================================================================

The PoolManager is SHARED between in-app and external swaps, so do NOT classify
on the PoolManager address. Two candidate signals were evaluated:

(1) Pool-id whitelist  — REJECTED as the *primary* signal.
    The external ETH/PITCH pool id is stable (acd168...), but:
      - A USDC/PITCH external pool may also exist (could not confirm one is live;
        its id would be a different keccak we cannot enumerate exhaustively).
      - Multi-hop aggregator routes (tx 0x2113baac) traverse SEVERAL unrelated V4
        pools in one tx (we saw bb2aef.., a87ce2.. besides acd168..), so matching
        "a swap in a whitelisted pool" is brittle and route-dependent.
      - New external pools (different fee/tickSpacing, or a future hooked router)
        would silently go unindexed.

(2) Counter-asset of the PITCH movement  — ADOPTED (this is what worked manually).
    Operate at the TRANSACTION level on PITCH ERC20 Transfer logs:

    For each tx that has >=1 PITCH Transfer touching the wallet:
      net_pitch_wallet = sum(PITCH in to wallet) - sum(PITCH out from wallet)   [wei]
      eth_value        = tx.value > 0                          (native ETH leg)
      has_weth         = any WETH Transfer log in the tx
      has_usdc         = any USDC Transfer log in the tx
      to_country_router= any PITCH transfer wallet->0x61cad011 (in-app sink)
      to_pack          = any PITCH transfer wallet->0x1acfa26b (pack opening)
      has_country_burn = any country/player-token Transfer to 0x0 (in-app 5% burn)

    Classify the tx as EXTERNAL iff:
        (eth_value OR has_weth OR has_usdc)        # a fiat/ETH counter-leg exists
        AND net_pitch_wallet != 0                   # wallet's PITCH balance changed
        AND NOT to_country_router                   # not an in-app PITCH->country buy
        AND NOT to_pack                             # not pack opening

      Then:
        if net_pitch_wallet > 0  ->  external_in  += net_pitch_wallet
        if net_pitch_wallet < 0  ->  external_out += -net_pitch_wallet

    Notes / why each guard:
      - Working at tx-level + net_pitch automatically DEDUPES multi-leg deliveries
        (tx 0x2113baac: 41.44 + 13.76 -> single +55.20).
      - The (eth_value OR has_weth OR has_usdc) gate is the "counter-asset is
        ETH-family" test. In-app trades never carry an ETH/WETH/USDC leg (counter
        asset is a country token), so they are excluded even though they share the
        PoolManager.  VERIFIED on all counter-examples above.
      - `to_country_router` is a belt-and-suspenders guard: an in-app buy sends
        PITCH to 0x61cad011 first; even if some future in-app path also moved ETH
        it would still be excluded. (On current data the ETH-leg gate alone is
        already sufficient.)
      - Plain transfers/airdrops have no ETH/WETH/USDC leg -> excluded.
      - A pure WETH<->USDC tx that happens to also touch PITCH for an unrelated
        reason is caught by net_pitch != 0 (no PITCH delta -> ignored).

    Edge case — wallet pays the DEX in WETH it already held (tx 0x2113baac shows
    WETH wallet->pool): has_weth=True catches it even with eth_value=False. Good.

    Edge case — wallet receives ETH/WETH/USDC AND PITCH in the same tx (e.g. an
    LP withdrawal): net_pitch would be +, eth/weth present -> would be miscounted
    as external_in. This is rare for retail wallets and flagged in OPEN QUESTIONS;
    a refinement is to additionally require a V4/V3 Swap log in the tx whose pool
    has PITCH as one currency. Recommend shipping the simple rule first.

PART C — ARCHITECTURE RECOMMENDATION
================================================================================

Three options were weighed:

  (A) Worker INDEXER + new table (mirror event_loop.py / backfill.py).
      + Scales; profile read stays cheap (one indexed SELECT).
      + Matches the established cursor/backfill pattern exactly.
      + Backfill is bounded: external trades = PITCH Transfer logs only, a LOW-
        volume topic (the whole-history scan of this one wallet returned only a
        few dozen logs). Scanning PITCH Transfer for the WHOLE token across all
        wallets is heavier but still far smaller than per-token candle data.
      - New subsystem: a scanner loop, a table, a migration, V4/tx classification
        code, and cold-start backfill cost.

  (B) ON-DEMAND per-wallet at /profile request time.
      + No table, no worker, no migration.
      - RPC-heavy in the hot path: per profile load we'd getLogs PITCH Transfers
        (to + from wallet) over the WHOLE chain history (chunked -> tens of
        getLogs), THEN fetch a receipt for every candidate tx to test for the
        WETH/USDC/ETH counter-leg (the Transfer-topic filter alone can't see
        tx.value or other-token legs). For an active wallet that's 20-60+ RPC
        round-trips per profile open. Profile is premium and already does a
        Multicall + balances RPC; adding this makes p95 load multi-second and
        couples UX latency to RPC health. REJECTED for the hot path.

  (C) HYBRID — indexer writes a per-wallet aggregate cache; compute lazily.
      Essentially (A) with a smaller table (just the two sums per wallet) OR (B)
      with a cache. Adds cache-invalidation complexity for little gain over (A).

RECOMMENDATION: (A) — a worker indexer writing a per-trade table.
  Rationale: the consumer (ROI) is read on every profile load (premium, latency-
  sensitive); the data source (PITCH Transfer logs) is low-volume and a natural
  fit for the existing cursor+backfill machinery; storing per-trade (not just the
  aggregate) keeps the door open to surfacing an external-trades list later and
  makes re-aggregation / corrections trivial. The marginal cost is one scanner
  tick + one table + one migration — all close clones of existing code.

  De-risk the cold-start: see Part E (start block + non-blocking backfill).


================================================================================
PART D — DATA MODEL (new table + migration)
================================================================================

Follows db-schema.sql conventions: CHAR(42)+CHECK addrs, CHAR(66)+CHECK tx_hash,
NUMERIC(78,0) for wei, UNIQUE(tx_hash) (NOT tx_hash+log_index — one external
trade may span multiple PITCH Transfer logs in a tx; we store one ROW PER TX).

  CREATE TYPE external_side AS ENUM ('in', 'out');   -- in = bought PITCH, out = sold

  CREATE TABLE external_pitch_trades (
      id              BIGSERIAL      PRIMARY KEY,
      block_number    BIGINT         NOT NULL,
      tx_hash         CHAR(66)       NOT NULL
                                     CHECK (tx_hash ~ '^0x[0-9a-f]{64}$'),
      wallet_address  CHAR(42)       NOT NULL
                                     CHECK (wallet_address ~ '^0x[0-9a-f]{40}$'),
      side            external_side  NOT NULL,
      -- net PITCH delta for the wallet in this tx (always positive magnitude, wei)
      pitch_wei       NUMERIC(78, 0) NOT NULL CHECK (pitch_wei > 0),
      -- the ETH-family counter asset spent/received, for future UI / audit.
      -- quote_token: lowercase address of WETH/USDC, or 0x0 for native ETH.
      quote_token     CHAR(42)       NOT NULL
                                     CHECK (quote_token ~ '^0x[0-9a-f]{40}$'),
      quote_wei       NUMERIC(78, 0) NOT NULL CHECK (quote_wei >= 0),
      ts              TIMESTAMPTZ    NOT NULL,
      CONSTRAINT external_pitch_trades_unique_tx UNIQUE (tx_hash)
  );

  -- Hot query: SUM(pitch_wei) per wallet per side.
  CREATE INDEX external_pitch_trades_wallet_idx
      ON external_pitch_trades (wallet_address, side);

Migration file (next after 0008_events_token_ts_idx):
  backend/migrations/versions/2026_05_31_xxxx-0009_external_pitch_trades.py
    revision      = "0009_external_pitch_trades"
    down_revision = "0008_events_token_ts_idx"
  upgrade(): CREATE TYPE external_side + CREATE TABLE + CREATE INDEX
             (idempotent style consistent with repo: use IF NOT EXISTS on index;
              guard the enum create with DO $$ ... EXCEPTION WHEN duplicate_object).
  downgrade(): DROP TABLE; DROP TYPE.

  NOTE on quote_wei for multi-asset routes: for the 0x2113baac case the wallet
  spent both WETH and (intermediate) USDC. Store the OUTERMOST asset the wallet
  actually paid (WETH here) as quote_token, and its wallet-side magnitude as
  quote_wei. quote_* is informational only — the ROI math uses pitch_wei. If a
  clean single quote can't be determined, store quote_token=0x0, quote_wei=0
  (the row is still valid for the PITCH aggregate).

PART E — WORKER CHANGES (new scanner, coexistence, backfill)
================================================================================

New module: backend/worker/external_loop.py  (mirror of event_loop.py)
New backfill: fold into existing backfill.run_if_needed OR a sibling
              external_backfill.run_if_needed (recommended: sibling, to keep
              the hook-event backfill untouched).

Cursor (separate from the hook cursor — app_state JSONB, same as last_scanned_block):
   app_state key  'external_last_scanned_block' -> {"block": N}
   app_state key  'external_backfill_status'     -> {complete, progressBlock, ...}
   Keeping a SEPARATE cursor is mandatory: the hook scanner cursor
   (last_scanned_block) advances independently and starts at HOOK_DEPLOY_BLOCK.

Start block:  EXTERNAL_DEPLOY_BLOCK — must be EARLIER than HOOK_DEPLOY_BLOCK!
   The first external buy (0x2113baac) is at block 46157923, ~9000 blocks BEFORE
   HOOK_DEPLOY_BLOCK (46167000). Pick a safe floor = the PITCH token / external
   pool creation block. Set conservatively (e.g. 46150000 or the PITCH pool init
   block) and make it a config env EXTERNAL_DEPLOY_BLOCK so it's tunable.

Scan strategy per tick (mirror event_loop.tick):
   1. head = block_number - reorg_lag.
   2. from = external_last_scanned_block + 1; bail if from > head.
   3. getLogs over [from, head] chunked (reuse chunk_blocks_default / fallback),
      filter:  address = PITCH,  topic0 = Transfer,
               (topic1 = wallet-padded OR topic2 = wallet-padded) is NOT used here
      -> we want ALL PITCH transfers in range, then group by tx and classify.
      For the live tick the volume is tiny (PITCH transfers are sparse).
   4. Group logs by tx_hash. For each tx with PITCH legs:
        - fetch the tx (eth_getTransactionByHash) for tx.value and tx.to,
        - fetch the receipt ONCE (eth_getTransactionReceipt) to see WETH/USDC
          Transfer legs and the to-country-router / to-pack / burn signals,
        - apply the Part-B rule -> emit (wallet, side, pitch_wei, quote_*, ts).
      (Optimization: only fetch receipt for txs that already have a PITCH leg to
      or from a NON-app address; skips the in-app country-router txs cheaply by
      first checking the PITCH Transfer counterparties.)
   5. INSERT ... ON CONFLICT (tx_hash) DO NOTHING  (idempotent, same as events).
   6. Resolve block timestamps once per unique block (reuse the _resolve_timestamps
      pattern from event_loop.py).
   7. Advance external_last_scanned_block = head.

   A tx can move PITCH for MULTIPLE wallets (e.g. a router batch). The rule keys
   net_pitch by the wallet that is a Transfer counterparty; emit one row per
   (tx, wallet) that nets non-zero AND passes the gate. (UNIQUE(tx_hash) above is
   therefore too strict if one tx legitimately moves external PITCH for two
   distinct wallets — change the constraint to UNIQUE(tx_hash, wallet_address)
   to be safe. RECOMMENDED: UNIQUE(tx_hash, wallet_address).)

Coexistence with the hook scanner:
   * Separate cursor + separate backfill status -> no interference.
   * Runs as its own external_loop.tick() in worker/main.py's loop, right after
     event_loop.tick(). Wrapped in its own try/except (operator_alerts pattern)
     so a failure never crashes the worker or the hook scanner.

Backfill / cold-start (the main risk):
   * backfill.run_if_needed is SYNCHRONOUS and blocks worker.main start (see its
     docstring). A naive external backfill that fetches a receipt per candidate
     tx over full history could be slow. Mitigations:
       - The candidate set is small: filter PITCH Transfers whose counterparty is
         NOT the country-router/pack/0x0 burn first; only those need a receipt.
       - Make the external backfill NON-blocking: run it incrementally inside the
         normal tick loop (advance progressBlock a chunk per tick) instead of a
         blocking pre-loop call, OR run it blocking but AFTER announcing worker
         start. Given ROI is a derived display metric (not safety-critical), a
         lazily-converging backfill is acceptable; the profile can show external
         ROI as it fills in.
       - Persist progressBlock after each chunk (resumable), exactly like
         backfill.py.
   RECOMMENDATION: incremental in-tick backfill (advance one chunk per tick until
   external_backfill_status.complete), so the worker never blocks on cold start.

PART F — API + ROI INTEGRATION (profile.py)
================================================================================

In backend/app/routes/profile.py get_profile(), after `wallet` is resolved:

  1. Load aggregates (one indexed query):
       SELECT side, COALESCE(SUM(pitch_wei),0) AS s
       FROM external_pitch_trades
       WHERE wallet_address = %s
       GROUP BY side;
     -> external_in_pitch  = to_display_units(sum where side='in')
        external_out_pitch = to_display_units(sum where side='out')

  2. value_pitch is already computed (current summary.totalValuePitch).

  3. New money-weighted ROI:
       denom = external_in_pitch
       money_weighted_roi =
           ((value_pitch + external_out_pitch - external_in_pitch) / denom * 100)
           if denom > 0 else None
     Guard denom==0 (wallet never bought PITCH externally) -> return None and let
     the frontend render "—". Do NOT divide by zero or fall back to the old gross
     ROI silently.

  4. New summary fields (additive — keep existing roiPct for backward compat or
     repurpose; recommend ADDING, not replacing, to avoid breaking other clients):
       summary.externalInPitch     : round(external_in_pitch, 2)
       summary.externalOutPitch    : round(external_out_pitch, 2)
       summary.moneyWeightedRoiPct : round(money_weighted_roi, 1) | null

     Optionally also expose summary.netExternalPitch = in - out for display.

  Cost: one extra indexed SELECT on external_pitch_trades. No RPC. Negligible.

  Note: positions/value already come from on-chain balanceOf (bug #11 fix), so
  value_pitch is a true current mark-to-market — consistent with money-weighted
  semantics.

PART H — OPEN QUESTIONS FOR THE PRODUCT OWNER
================================================================================

1. TRANSFERS to other wallets — counted as external_out?
   Current rule: NO (a plain transfer has no ETH/WETH/USDC counter-leg, so it is
   neither external_in nor external_out). That means moving PITCH to a second
   personal wallet, or paying someone in PITCH, does NOT reduce external_in. For
   a strict money-weighted ROI of THIS wallet that is arguably correct (no cash
   realized). Confirm. If transfers-out should count as disposals at some
   reference price, that's a different (and fuzzier) metric.

2. CEX flows. Deposits to / withdrawals from a CEX are plain transfers on-chain
   (no DEX swap), so they are excluded. A user who bought PITCH on a CEX and
   withdrew it has external_in = 0 and thus money_weighted_roi = None. Acceptable?
   (We cannot see the CEX-side fiat. Recommend: show "—" with a tooltip rather
   than a misleading number.)

3. BACKFILL depth. How far back must external trades be indexed? The earliest
   external buy we found predates HOOK_DEPLOY_BLOCK. Set EXTERNAL_DEPLOY_BLOCK to
   the PITCH external-pool creation block (full history) vs a recent cutoff
   (cheaper, but truncates external_in for early adopters and inflates ROI).
   Recommend full history from pool creation.

4. V4 decoding complexity. We deliberately classify by ERC20 Transfer + tx.value
   + receipt scan (Part B), NOT by decoding V4 Swap event amounts. This avoids
   the V4 amount-sign / currency-ordering / multi-hop-route complexity entirely
   and was the approach that reproduced all 4 known buys. Confirm we are happy to
   rely on the Transfer/counter-asset heuristic rather than full V4 swap decoding.
   (Decoding V4 Swap amounts directly would be needed only if we later want the
   exact ETH/USD price per trade.)

5. Multi-asset / LP edge case. A tx where the wallet RECEIVES both PITCH and
   ETH/WETH/USDC (e.g. removing liquidity, or a refund) could be miscounted as
   external_in. Rare for retail. Ship simple rule first, or add the optional
   refinement "require a V4/V3 Swap log in a PITCH pool in the same tx"? Confirm
   risk tolerance.

6. New external venues. If pitchwc lists PITCH on another DEX/router later, the
   counter-asset rule still catches it (any ETH/WETH/USDC leg) WITHOUT a code
   change — but a brand-new quote asset (e.g. a different stablecoin) would need
   to be added to the WETH/USDC/ETH whitelist. Confirm the stablecoin set to
   support (USDC only, or also USDbC / DAI / etc.).

7. external_out price/denomination. external_out is measured in PITCH COUNT
   (PITCH sold), consistent with external_in. The ROI formula keeps everything in
   PITCH, so no fiat conversion is needed. Confirm this is the intended unit (vs
   converting in/out to a fiat/ETH basis).
