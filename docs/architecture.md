## 1. Назначение и контекст

PitchTerminal — браузерный просмотрщик и торговая панель для рынков токенов игроков и
стран pitchwc.app на блокчейне Base (L2, chain ID 8453). Существуют две версии:

- **Портативная** (`PitchTerminal`, публичный репозиторий) — однопользовательская,
  кастодиальная (подписывает приватным ключом из `.env`), запускается локально. Это
  бесплатный self-host-вариант. Заморожена, развивается независимо.
- **Веб** (`PitchTerminal-web`, приватный репозиторий) — предмет этого документа.
  Монетизируемое многопользовательское **некастодиальное** приложение: пользователи
  подключают свой кошелёк, сервер не хранит их приватных ключей.

Это **жёсткий форк**: общего кода между версиями нет, портативный код служит
референсом (ABI, ценовая логика, декод событий), а не зависимостью.

## 2. Цели, принципы и ограничения

**Цель** — монетизируемый веб-продукт: просмотр графиков рынка бесплатно, торговля и
аналитика — за разовую оплату 1 PITCH.

**Сквозные принципы:**

- **Некастодиальность.** Сервер не хранит приватных ключей пользователей. Единственный
  ключ на сервере — gas-кошелёк кипера (только для оплаты газа, см. §15).
- **Минимум переписываний.** У приложения конечный срок жизни (привязан к ЧМ) — рабочий
  код сохраняем, переписываем только необходимое.
- **Минимум компонентов.** Solo-разработчик: чем меньше движущихся частей, тем лучше.
- **Документация и анализ до реализации.**

**Ограничения:** один разработчик; конечный срок жизни; бюджет близок к нулю (единственная
неизбежная статья — VPS ~$5/мес).

### 2.1 Числовые дефолты (сводка)

Полные значения и где они конфигурируемы — в [conventions.md](conventions.md) §9
(env vars). Здесь — для быстрой сверки:

| `FEE_BPS` (комиссия pitchwc) | 500 (5%) | Расчёт `minOut` в executor'е |
| Freshness threshold | 30 с | Индикатор устаревших данных |
| Keeper gas alert порог | 0.01 ETH | Operator-Telegram алерт |

| `getLogs` chunk (public RPC) | 2000 блоков | Fallback |
| JWT TTL | 72 часа | После — повторный SIWE |
| SIWE nonce TTL | 5 минут | Replay protection |

| Cache `hasAccess=false` TTL | 30–60 с | API-кэш |
| Pagination default `limit` | 100 | API |
| Pagination max `limit` | 500 | API |
| SSE heartbeat | 25 с | Защита от idle-разрыва прокси |
| SSE max connections | 5 / IP, 2 / address | Anti-abuse |

**Продуктовые решения:**

- **Язык интерфейса** — английский, один язык; интернационализация (i18n) — кандидат на
  пост-MVP. Аудитория ЧМ глобальная, web3 по умолчанию англоязычный.
- **Юридический дисклеймер** — короткая страница, ссылка в футере + строкой в окне
  оплаты: не финансовый совет, торговля на свой риск, токены высокоспекулятивны;
  некастодиально (мы не храним средства и ключи); оплата 1 PITCH невозвратна;
  PitchTerminal — независимый инструмент, не аффилирован с pitchwc.
- **Ожидаемый масштаб (НФР)** — нишевый инструмент в рамках ЧМ: реалистично десятки–сотни
  одновременных пользователей на пике, ~сотни одновременных SSE-соединений. Спроектированная
  архитектура (gevent, один worker, Postgres, один VPS) держит это с запасом. Ориентиры:
  задержка чтения API < 100 мс, обновления раз в ~5с. Путь масштабирования при кратном
  росте: больше API-процессов / VPS мощнее / добавить Redis — не ожидается.

## 3. Модель монетизации

Разовая разблокировка за **1 PITCH** на адрес кошелька, **навсегда** (без истечения —
приложение живёт в рамках ЧМ). Free-уровень — просмотр графиков; premium — торговля,
портфолио, лимит-ордера, алерты.

Платёж — обычный перевод через смарт-контракт `PitchTerminalAccess` (§5.1). Сервер только
читает on-chain статус `hasAccess(addr)` — биллинг-инфраструктура не нужна.

### 3.1 Бесплатно vs премиум

| Уровень | Что входит |
|---|---|
| **FREE** (без логина) | Списки токенов, поиск, фильтры, графики (свечи/линия, таймфреймы), вкладки Trades и Holders, change%, SSE-каналы `prices`/`events` |
| **PREMIUM** (1 PITCH) | Торговля, портфолио/PnL (`/api/profile`, `myWallet`), лимит-ордера, алерты |

### 3.2 Жёсткие и мягкие замки

Правило (механическое, без оценочных суждений): **есть ли за функцией серверный эндпоинт
или серверный процесс?** Да → жёсткий замок (`@require_premium`, сервер отдаёт 403). Нет
(только браузер ↔ блокчейн) → мягкий замок (фронт прячет UI).

- **HARD** — `/api/profile`, поле `myWallet` в `/api/trades`, `/api/orders*`, SSE-канал
  `orders`, кипер лимит-ордеров, отправитель алертов. Обойти нельзя.
- **SOFT** — торговая панель, котировки, отображение балансов, личные оверлеи графика.
  Грамотный пользователь обойдёт — и это нормально: честная альтернатива «скачай
  портативную версию» делает paywall монетизацией удобства, а не DRM.

Ключевой ход, убирающий неоднозначность: эндпоинты `/api/trade`, `/api/quote`,
`/api/wallet` **удаляются** — браузер торгует напрямую с контрактами, у торговли не
остаётся серверной поверхности.

## 4. Топология системы

```
        Браузер(ы) пользователей
          │ REST + SSE             │ подпись tx / чтение
          │ (данные, SIWE)         │ котировок и балансов
          ▼                        ▼
   ┌─────────────────────┐   ┌───────────────────────────┐
   │  API-сервер          │   │      Base L2 (chain)       │
   │  1..N процессов      │   │  Router · Hooks · PITCH    │
   │  REST · SSE          │   │  Multicall3                │
   │  (чейн НЕ опрашивает) │   │  PitchTerminalAccess       │
   └────┬───────────▲─────┘   │  LimitOrderExecutor        │
  чтение│           │ pub/sub └─────────────▲──────────────┘
        ▼           │ (broadcast)           │ опрос чейна (RPC)
   ┌────────────────┴─────┐                 │
   │   Postgres            │                │
   └──────────▲───────────┘                 │
      запись  │                             │
   ┌──────────┴──────────────────────────────┴──┐
   │  Background worker (1 процесс)               │
   │  collector · keeper · alert sender           │
   └───────────────────────┬──────────────────────┘
                            ▼
                     Telegram (бот)
```

**Компоненты:**

- **Background worker** (1 процесс) — единственное, что опрашивает блокчейн. Сборщик
  данных (циклы цен/событий), кипер лимит-ордеров, отправитель алертов. Пишет в Postgres.
- **API-сервер** (1..N процессов) — «тонкий»: REST + SSE, держит SSE-соединения, читает
  из Postgres, сам чейн не опрашивает.
- **Postgres** — общее хранилище между worker и API; источник истины и канал pub/sub.
- **Base L2** — контракты pitchwc + наши два контракта.
- **Telegram** — доставка алертов от worker'а.

Браузер имеет два независимых канала: REST+SSE к нашему API; напрямую к чейну через
кошелёк (подпись сделок, чтение котировок/балансов).

**Почему worker отделён от API:** при нескольких API-процессах каждый запускал бы свой
цикл цен → N-кратное дублирование RPC-нагрузки и рассинхрон данных. Один collector-worker
обязателен, а не опционален.

## 5. Смарт-контракты

Два собственных контракта, оба на Foundry, на базе OpenZeppelin. Единственный новый
Solidity в проекте.

### 5.1 PitchTerminalAccess

Контракт доступа (≈50 строк):

- `buyAccess()` — `pitch.transferFrom(msg.sender, treasury, price)`, ставит
  `paid[msg.sender] = true`. Деньги идут **сразу в treasury**, контракт ничего не хранит
  (минимальная поверхность атаки, метод `withdraw` не нужен). Требует предварительного
  `approve` ровно на `price` → 2 попапа в кошельке.
- `hasAccess(addr) view` → `paid || whitelisted`.
- `grantAccess` / `grantBatch` / `revokeAccess` — onlyOwner whitelist для бесплатного
  доступа (друзья, тестеры, giveaway).
- `setPrice`, `transferOwnership` — onlyOwner. `price` настраиваемый (курс PITCH плавает).

Контракт — **оракул, а не охранник**: он отвечает «есть ли доступ», но соблюдение этого
ответа — на сервере (жёсткие функции) и клиенте (мягкие).

### 5.2 LimitOrderExecutor

Контракт авто-исполнения лимит-ордеров (§10). Ордер — это off-chain подписанное
EIP-712-сообщение; контракт проверяет подпись (ECDSA + EIP-1271), цену у Hook'а, срок и
nonce, затем тянет токены пользователя, делает своп через Router pitchwc и отдаёт
результат. Permissionless-функция `execute(order, signature)`. Эмитит
`OrderExecuted(user, …)` для атрибуции. Двигает средства пользователей → **обязателен аудит**.

### 5.3 Кошельки и роли

Три отдельных кошелька — никогда не смешиваем «деньги» и «админ» в одном ключе:

| Кошелёк | Роль | Где | Экспозиция |
|---|---|---|---|
| Торговый (shaburshila.base.eth) | Торговля на сайте | у пользователя | высокая |
| **Treasury** (свежий) | Приём выручки PITCH | у пользователя | низкая |
| **Owner** (свежий) | Админ контрактов (whitelist, цена) | у пользователя | минимальная |
| Keeper gas-кошелёк | Оплата газа за `execute()` | на сервере | только газ |

Owner управляет whitelist и ценой, **не деньгами** → утечка owner-ключа не ведёт к
потере средств.

**Как owner выполняет операции:** через Foundry-скрипты в `contracts/script/`
(`Whitelist.s.sol`, `SetPrice.s.sol`, `TransferOwnership.s.sol`). Owner-ключ
хранится только в кошельке пользователя (например, hardware-кошелёк);
запускается локально:
```
forge script script/Whitelist.s.sol --rpc-url $RPC_URL --broadcast \
  --ledger --sender 0x<OWNER>
```
Никакого admin-UI в веб-приложении нет — это сокращает атаку и упрощает аудит.
Whitelist пополняется батчами (`grantBatch(address[])`, ≤100 адресов за tx).

### 5.4 Инструментарий и деплой

- **Foundry** — Solidity-тесты, самодостаточный инструмент.
- Деплой: Foundry-тесты (с mock-PITCH) → Base mainnet → **верификация на Basescan**
  (пользователи отправляют 1 PITCH — должны видеть исходник).
- Деплой контрактов — отдельное ручное разовое действие, **не часть CI/CD**.

## 6. Бэкенд

Язык — Python. Один кодовый репозиторий, **две точки входа и два процесса**.

### 6.1 API-сервер

- **Flask** — сохраняем существующие роуты; меняется только способ запуска.
- Запуск под **gunicorn + gevent** — greenlet'ы вместо потоков ОС держат тысячи
  SSE-соединений.
- Раздаёт REST + SSE, держит соединения, читает из Postgres. Чейн не опрашивает.

### 6.2 Worker

Обычный Python-скрипт (без веб-фреймворка): циклы цен/событий, кипер лимит-ордеров,
отправитель алертов. Единственный потребитель нашего RPC.

### 6.3 Общий код

`backend/shared/` — config, web3-хелперы, БД-слой, модели, ценовая логика, декод событий,
PnL, SIWE-проверка. Используется и API, и worker'ом.

### 6.4 API и SSE

REST-API под префиксом `/api/v1/`. Ответы — JSON (camelCase); ошибки — RFC 7807
(`application/problem+json`); rate-limit → `429 + Retry-After`; неизвестный токен → 404.
Premium-эндпоинты — декоратор `@require_premium` (401 — не залогинен, 402 — не оплатил).
Растущие списки (история сделок, сделки в профиле) — с пагинацией.

| Эндпоинт | Метод | Доступ | Назначение |
|---|---|---|---|
| `/` | GET | FREE | SPA |
| `/api/v1/config` | GET | FREE | Bootstrap-конфиг фронта (chainId, адреса, цена, WC projectId) |
| `/api/v1/tokens` | GET | FREE | Списки токенов (игроки + страны) |
| `/api/v1/tokens/{token}/chart` | GET | FREE | Свечи/точки; `?tf=` |
| `/api/v1/tokens/{token}/trades` | GET | FREE | История сделок + холдеры (пагинация) |
| `/api/v1/tokens/{token}/position` | GET | PREMIUM | PnL подключённого кошелька по токену |
| `/api/v1/stream` | GET | FREE | SSE-поток (канал `orders` — только premium) |
| `/api/v1/auth/nonce` | GET | — | SIWE-nonce |
| `/api/v1/auth/verify` | POST | — | Проверка SIWE-подписи, выдача JWT-cookie |
| `/api/v1/auth/logout` | POST | AUTH | Сброс сессии |
| `/api/v1/access` | GET | AUTH | Статус доступа; `?fresh=1` — в обход кэша (rate-limit) |
| `/api/v1/profile` | GET | PREMIUM | Портфолио (сделки — пагинация) |
| `/api/v1/orders` | GET / POST | PREMIUM | Список / создать ордер (подписанный; дедуп owner+nonce) |
| `/api/v1/orders/{id}` | DELETE | PREMIUM | Отмена ордера (server-side) |
| `/api/v1/orders/armed` | PUT | PREMIUM | Персональный kill-switch |
| `/api/v1/telegram/webhook` | POST | — | Webhook Telegram-бота — **добавляется в фазе 3** |

Удалены относительно портативной версии: `/api/trade`, `/api/quote`, `/api/wallet`
(торговля ушла в браузер), ручной `execute` ордера (исполнение — это кипер).

**SSE** — один поток `GET /api/v1/stream` (`text/event-stream`), три канала:

| Канал | Доступ | Когда | Нагрузка |
|---|---|---|---|
| `prices` | FREE | ~5с | Дельта рыночного снимка — только изменившиеся токены |
| `events` | FREE | ~5с | Новые сделки Buy/Sell |
| `orders` | PREMIUM | при смене статуса | Обновления статусов ордеров пользователя |

- Авторизация — httpOnly-cookie (`EventSource` прикладывает сам); `orders` отдаётся только
  premium-сессиям. Набор каналов фиксируется при подключении — при разблокировке premium
  фронт переподключает SSE.
- **Heartbeat** — keep-alive комментарий каждые ~20–30с, чтобы прокси не рвали idle-
  соединение. Поток сжимается (Caddy).
- Реконнект — нативный `EventSource` + fallback; при переподключении фронт дотягивает
  состояние обычными GET. Начальное состояние при загрузке — тоже через GET; SSE несёт
  только обновления.
- Рассылку питает worker через Postgres `LISTEN/NOTIFY` (§7.4).

## 7. Доменная модель и хранение данных

### 7.1 Доменная модель

- **Токены — два вида:** игроки и страны. 48 стран, 144 игрока (3 на страну: best /
  captain / rookie). Все — ERC20, 18 decimals. Базовый токен экосистемы — **PITCH**
  (фиксированная эмиссия 960 000).
- **Ценовая цепочка:** цена токена игрока выражена в токене его страны; цена токена
  страны — в PITCH. Итого `player_price_pitch = player_price_country × country_price_pitch`.
- **Ценообразование:** bonding curve через хуки Uniswap V4. На каждой сделке **5%
  сжигается** в токене страны — это комиссия протокола pitchwc, не нашего терминала.
- **Две цены:** *рыночная* (для графиков) — цена кривой без комиссии; *эффективная*
  (для истории сделок) — с учётом 5%.
- **Вычисляемые метрики:** change% (6 периодов), число холдеров, число сделок, PnL
  (realized / unrealized, **avg-cost basis** — средневзвешенная цена покупки;
  `avg_buy = total_spent / total_bought`, `realized = received - avg_buy * sold`),
  средние цены входа. Avg-cost — не FIFO; формулы — в
  [port-from-portable.md](port-from-portable.md), реализация — `shared/pnl.py`.
- **Маппинг «игрок → страна»** берётся из seed-данных (`tokens.country_address`), а не из
  on-chain `getBaseCurrency` — он реверитит для части токенов.

### 7.2 Хранилище

**Единое — Postgres** (отклонены: Redis как второй компонент; документные БД — данные
реляционные; SQLite — неудобен при нескольких процессах). Личность = адрес кошелька,
premium — on-chain, сессии — stateless JWT, поэтому **таблицы `users` нет**: персональные
данные привязаны к адресу. Платежи в БД не дублируются — источник истины `hasAccess` в
контракте.

### 7.3 Схема БД

**Соглашения:** суммы и цены (wei, uint256) — `NUMERIC(78,0)`, хранится сырое целое
(никогда не `bigint`/`float`); адреса — `CHAR(42)` в нижнем регистре (checksum — только
на отображение); время — `TIMESTAMPTZ` (UTC); контролируемые значения — `ENUM`/`CHECK`;
суррогатные PK высоконагруженных таблиц — `bigint`.

| Таблица | Назначение | Ключевые поля / примечания |
|---|---|---|
| `tokens` | Статичные метаданные токенов (seed из tokens.json) | address (PK), name, symbol, kind (ENUM player/country), country_address (self-FK, NULL у стран), role (NULL у стран) |
| `events` | Все Buy/Sell — питает графики, сделки, холдеров, PnL | id (bigint PK), block_number, tx_hash, log_index, token_address (FK), side, trader_address, base_value, token_value, fee, ts. UNIQUE (tx_hash, log_index) → идемпотентность пере-сканов. Индексы: (token_address, block_number), trader_address |
| `market_state` | **Derived/cache** — динамика по токену, пересчитываема. Пишет worker, читает API | token_address (PK, FK), price_country, price_pitch, supply, change_pct (6 периодов), trades_count, updated_at |
| `app_state` | Key-value служебное состояние | key (PK), value — курсор скана (last_scanned_block), будущие флаги |
| `limit_orders` | Подписанные лимит-ордера + статус | id (bigint PK), owner_address, token_address (FK), side (ENUM), target_price, amount, slippage_bps, expires_at (nullable), nonce, signature, status (ENUM), created_at, executed_tx_hash, fail_reason. UNIQUE (owner_address, nonce). Частичный индекс WHERE status='pending' |
| `auth_nonces` | Одноразовые SIWE-nonce | nonce (PK), created_at. Delete-on-use + периодическая чистка протухших (~5 мин) |
| `user_settings` | Персональные настройки | owner_address (PK), orders_armed (kill-switch). Расширяемо |
| `telegram_links` | Связка chatId ↔ кошелёк — **добавляется в фазе 3** (Telegram пост-MVP) | owner_address (PK), chat_id, linked_at |

`events` за весь срок жизни — десятки–сотни тысяч строк, партиционирование не нужно.

### 7.4 SSE pub/sub и сессии

**SSE pub/sub** — Postgres `LISTEN/NOTIFY`: worker шлёт сигнал «обновлено», каждый
API-процесс подтягивает свежие данные и рассылает своим SSE-клиентам. Под gevent драйверу
нужен `psycogreen.gevent.patch_psycopg()`.

Сессии — stateless JWT, серверного хранилища сессий нет.

## 8. Аутентификация и контроль доступа

### 8.1 SIWE-вход

Sign-In With Ethereum (EIP-4361) — вход по подписи кошельком, без паролей:

1. Пользователь подключает кошелёк.
2. Фронт запрашивает у сервера nonce.
3. Кошелёк подписывает SIWE-сообщение (домен, адрес, chain ID 8453, nonce, время).
4. Сервер проверяет подпись, nonce, домен/сеть → выдаёт JWT.

Nonce хранится в крошечной таблице Postgres (TTL ~5 мин, помечается использованным —
защита от replay). Smart-contract кошельки (Coinbase Smart Wallet, Safe) проверяются
через **EIP-1271** `isValidSignature`.

### 8.2 Сессии (JWT)

Stateless JWT, подписанный секретом сервера. Срок жизни — **3 дня**. Доставка — **httpOnly
cookie** (`SameSite=Lax` + `Secure`): JS не может прочитать токен (защита от XSS), а
нативный `EventSource` сам прикладывает cookie — SSE-авторизация работает без переписывания
клиента. Same-origin (Caddy отдаёт фронт и API с одного домена) снимает CORS.

JWT хранит только адрес кошелька. Статус premium проверяется отдельно (§8.3).

### 8.3 Слой проверки доступа

Декоратор `@require_premium` на премиум-эндпоинтах. Адрес берётся из JWT.

- **Кэш `hasAccess` в памяти API-процесса.** Значения попадают в кэш только из честного
  чтения контракта — клиент в него писать не может.
- **Асимметричный TTL:** `true` → ~1 час (`whitelisted` может быть отозван); `false` →
  ~30–60 с (пользователь может оплатить в любой момент).
- **Fail-open при сбое перепроверки:** если запись `true` протухла, а перепроверка по RPC
  не удалась — сохраняем старый `true`, не отказываем платящему из-за икоты RPC.
- **Коды:** 401 — не залогинен (фронт → «подключить кошелёк»); 402 Payment Required —
  залогинен, но не оплатил (фронт → баннер оплаты).
- **Мгновенная разблокировка:** после подтверждения платёжной tx фронт дёргает refresh-
  эндпоинт с прямой проверкой `hasAccess` в обход кэша. Эндпоинт под rate-limit.

## 9. Клиентский торговый слой

Вся торговля — в браузере, напрямую с контрактами (сервера в пути нет).

- **Библиотеки:** `@wagmi/core` + viem; коннекторы `injected` (десктоп-расширения) и
  `walletConnect` (мобильные через QR).
- **Сеть:** если кошелёк не на Base (8453) — предложить переключиться/добавить сеть;
  торговая панель заблокирована до переключения.
- **Поток сделки:** котировка читается у Hook'а (`quoteBuy`/`quoteSell`) → клиент считает
  `minOut = котировка × (1 − slippage)` → при необходимости `approve` → `Router.buy/sell`
  подписывается в кошельке → ожидание receipt. Балансы/allowance читаются напрямую через
  viem + Multicall3.
- **Approve:** для торговли — **max-approve** Router'у (один approve на токен, дальше
  сделки в 1 попап); кто хочет — сам понизит allowance в кошельке.
- Своя сделка появляется на графике в течение ≤5 с (сканер событий worker'а + SSE).

## 10. Лимит-ордера и кипер

Лимит-ордера **исполняются автоматически** — это ядро PitchTerminal. Авто-исполнение
сделано некастодиально через **контракт `LimitOrderExecutor`** (отклонён вариант с
session keys — горячие ключи на сервере проигрывают по безопасности, устойчивости и
красоте разработки).

**Механика:** ордер — это off-chain подписанное EIP-712-сообщение (создание бесплатно и
мгновенно, без транзакции), хранится в Postgres. Worker-кипер на каждом ценовом тике
проверяет цели; при срабатывании вызывает permissionless `execute(order, signature)`.
Контракт проверяет подпись, `currentPrice`, срок и nonce, тянет токены пользователя (по
заранее данному `approve`), свопает через Router, отдаёт результат. Проверка и своп —
**атомарно в одной транзакции**, гонки нет. Отмена ордера — бесплатно (server-side) либо
on-chain.

- Виды: лимит-buy (триггер снизу) и take-profit (триггер сверху). Стоп-лосс не делаем.
- **TTL:** опциональная экспирация — «без срока» или пресет: 15м / 30м / 1ч / 3ч / 6ч /
  12ч / 24ч / 3 суток / 7 суток.
- **Per-user kill-switch** — каждый пользователь ставит свои ордера на паузу сам.
- Газ за `execute()` платит оператор (на Base — копейки).

Выполнимость подтверждена on-chain (2026-05-22): контракты pitchwc верифицированы, у
`buy`/`sell` нет ограничений на вызывающего. Остаётся ранний end-to-end тест с реальными
токенами на этапе реализации.

## 11. Алерты

**Два независимых канала** — оператору (с MVP) и пользователям (фаза 3). Оба через
Telegram, через **разные боты**. Мотивация — структурная чистота, не безопасность
(оба секрета лежат рядом в `.env`, компрометация сервера выдаёт оба):

- Operator-бот — **outbound only**, webhook ему не нужен. `setWebhook` не зовём.
- User-бот — **с webhook'ом**, принимает `/start <token>` от пользователей.
- Раздельные namespace ловят случайные cross-routing-баги: попытка отправить
  user-сообщение через operator-бот сразу упадёт (токен не уполномочен).
- Operator-бот не упоминается в UI — публично известен только user-бот.

Цена решения — два `setup`а у BotFather и пары env (см. `OPERATOR_TG_*` и
`USER_TG_*` в [conventions.md](conventions.md) §9).

### 11.1 Operator alerts (MVP)

Оператор (= единственный человек, владелец проекта) подписан в личный Telegram-чат
на критические события worker'а. Доступен с фазы 0 — без webhook'ов, только
outbound `sendMessage`.

- Env vars: `OPERATOR_TG_BOT_TOKEN`, `OPERATOR_TG_CHAT_ID` (см.
  [conventions.md](conventions.md) §9).
- События: газ keeper-кошелька ниже `KEEPER_GAS_THRESHOLD_WEI`; данные устарели
  > 5 минут; необработанное исключение в worker'е; повторяющиеся сбои RPC; реверт
  `execute()` с неожиданной причиной.

### 11.2 User alerts (фаза 3)

Вторичная фича. Архитектура резервирует точку стыковки; webhook добавляется в
фазе 3.

- Канал — **только Telegram** (browser push отложен).
- Привязка: premium-пользователь жмёт «Подключить Telegram» → deep-link
  `t.me/Бот?start=<одноразовый-токен>` → бот получает `/start`, webhook на
  API-сервере (`/api/v1/telegram/webhook/<secret>`, см. [api-spec.md](api-spec.md) §10)
  сопоставляет токен с адресом → связка `chatId ↔ wallet` в Postgres
  (`telegram_links`).
- Исходящие — worker вызывает Telegram `sendMessage` напрямую (без бот-фреймворка).
- События: ордер исполнился / не прошёл / истёк.

## 12. RPC и нагрузка

**Картина нагрузки:** worker — единственный потребитель нашего RPC (цикл цен + сканер
событий + редкие `hasAccess`); нагрузка постоянна, не зависит от числа пользователей.
Анонимные посетители грузят только Postgres. Торговля браузера идёт через RPC кошелька
пользователя.

**RPC:** бесплатный тариф **Alchemy** как primary + публичный `mainnet.base.org` как
fallback. Денег не тратим, получаем надёжность, высокие лимиты и щедрый `eth_getLogs`
(нужен для исторического бэкфилла событий).

## 14. Инфраструктура и развёртывание

### 14.1 Хостинг

Один **платный VPS** (Hetzner / DigitalOcean): API + worker + Postgres на одной машине под
**Docker Compose**. **Caddy** — реверс-прокси с автоматическим HTTPS (Let's Encrypt),
отдаёт статику и проксирует `/api` (same-origin, нужно для cookie).

**Caddy с кастомным билдом.** Базовый Caddy не имеет директивы `rate_limit` —
это сторонний модуль (`github.com/mholt/caddy-ratelimit`). Используем
`xcaddy build` с этим модулем; готовый бинарник кладём в Docker-образ Caddy.
Альтернатива — отказаться от Caddy-уровня rate-limit и полагаться только на
`flask-limiter` в API. Решение: оставить Caddy rate-limit для защиты до
прихода запроса в Flask (анти-DoS по статике, по `/api/v1/stream`).

### 14.2 CI/CD

**GitHub Actions.** Push в `main` → прогон тестов (гейт) → сборка (Vite-фронт + Docker-
образ бэкенда) → публикация в GitHub Container Registry (ghcr.io) → VPS подтягивает образ
+ `docker compose up -d`. Теги образов дают откат одной командой.

### 14.3 Окружения и тестирование

Локальная разработка + один продакшен-VPS. Staging нет — страховка состоит из:
тест-гейт CI + **post-deploy smoke-проверка** + откат по тегу образа.

**Стратегия тестирования** (риск-взвешенная, а не «процент покрытия»):
- Смарт-контракты — близко к 100%, все ветки (высшие ставки, неизменяемы).
- Чистая логика бэкенда (ценовая цепочка, PnL avg-cost, декод событий, проверка доступа,
  триггеры ордеров, SIWE) — плотные unit-тесты.
- Критичные эндпоинты — интеграционные тесты.
- Клей (Flask/SSE, vanilla-фронт) — легко: smoke + ручная проверка.

Бэкапы — ночной `pg_dump` по cron, **загрузка на off-site хранилище** (B2/R2/S3/rsync.net).
Local-only = single point of failure (VPS погиб → данные потеряны). См.
[plans/infra.md](plans/infra.md) I0.7.

## 15. Безопасность

- **Ключи на сервере:** единственный — keeper gas-кошелёк. Он держит только газ и может
  вызывать лишь permissionless `execute()` → утечка ≈ потеря пары долларов ETH, средства
  пользователей не под угрозой. Owner / treasury / торговый кошельки — НЕ на сервере.
- **Секреты** (JWT-секрет, Telegram bot token, ключ Alchemy, пароль Postgres, ключ
  keeper, WalletConnect project ID): никогда в коде/git — `.env` на VPS (в `.gitignore`)
  + GitHub Actions secrets для пайплайна.
- **Rate limiting:** flask-limiter на auth / refresh / создание ордеров; лимиты Caddy на
  публичные эндпоинты и SSE-соединения на IP.
- **CORS:** same-origin by design — никаких разрешающих CORS-заголовков.
- **Контракты:** оба — ревью/аудит до mainnet-деплоя.
- Параметризованные SQL-запросы, валидация входных данных.

## 19. Эксплуатация и отказоустойчивость

### 19.1 Обработка ошибок и режимы отказа

| Сбой | Поведение |
|---|---|
| Реверт сделки в браузере (slippage, нет баланса) | Состояние чейна не изменилось (атомарно); фронт — понятная ошибка + повтор |
| Отклонён попап кошелька | Поток прерывается чисто, без изменений |
| Сбой RPC (worker) | Тик пропущен → ретрай на следующем (worker не падает); данные устаревают → индикатор свежести. Fallback на публичный Base RPC при повторных сбоях |
| Падение worker | API отдаёт последние данные из Postgres (с индикатором свежести); Docker-restart; возобновление скана с `app_state.last_scanned_block` (вставки идемпотентны) |
| Падение API-процесса | Прочие процессы / Docker-restart; SSE-клиенты переподключаются |
| Реверт `execute()` — **цена ушла за условие** | Ордер остаётся **`pending`** — цель может сработать снова; НЕ `failed` |
| Реверт `execute()` — терминальный (нет средств, отозван approve) | Ордер → `failed` (с причиной, если декодируема) |
| Истёк TTL ордера | Ордер → `expired` |
| Транзиентный сбой подачи `execute()` | Ретрай на следующем тике |
| Застрявшая транзакция кипера | Ожидание receipt с таймаутом → переподача тем же nonce с повышенным газом (replacement-tx) |
| Postgres недоступен | Жёсткий отказ (одна машина) — restart-политика, бэкапы, алерт оператору |
| Реорг Base (L2) | Митигация — **лаг подтверждения** (скан немного позади head); `UNIQUE(tx_hash,log_index)` — это идемпотентность пере-сканов, отдельная от реоргов |

Worker — **синглтон** (Docker Compose запускает ровно один). Даже если бы запустился
второй кипер, per-order nonce контракта не даст исполнить ордер дважды (бэкстоп).

### 19.2 Наблюдаемость и операции

- **Health-эндпоинт** `GET /api/v1/health` — 200, если API и БД доступны; свежесть данных
  — поле в ответе (не код 200/500). Используется post-deploy smoke-проверкой и внешним
  аптайм-монитором.
- **Логи** — структурированные, в stdout (Docker собирает); ротация драйвером Docker
  (`max-size` / `max-file`), чтобы не забить диск.
- **Алерты оператору** — worker шлёт критические события в **личный Telegram-чат
  оператора**: газовый кошелёк кипера на исходе, worker завис (данные устарели сверх
  порога), повторяющиеся сбои RPC, необработанные исключения. Операторский канал = бот +
  chat id оператора; доступен с MVP (тривиальный outbound `sendMessage`), независим от
  пользовательского Telegram (фаза 3).
- **Без тяжёлого стека метрик** (Prometheus и т.п.) — для solo-проекта на конечный срок
  достаточно: логи + health + аптайм-монитор + Telegram-алерты оператору.
- Монитор баланса keeper-кошелька — скрипт из `scripts/`.

### 19.3 Первоначальный бэкфилл событий

На первом деплое `events` пуста — worker одноразово бэкфиллит историю Buy/Sell с
`HOOK_DEPLOY_BLOCK` (46 167 000) до текущего блока, **по обоим хукам сразу одним
проходом** (один курсор `app_state.last_scanned_block`; флаг `country_backfilled` из
портативной версии — артефакт ретрофита, в веб-версии не нужен).

- Скан чанками; вставка идемпотентная (`ON CONFLICT DO NOTHING`) → бэкфилл возобновляем
  при рестарте по курсору.
- **Скорость:** на Alchemy чанки `getLogs` крупнее, пауза между вызовами минимальна
  (портативные 2000 блоков + 0.2с подобраны под публичную ноду). Размер чанка адаптивный —
  при превышении лимита по числу логов чанк уменьшается.
- Бэкфилл — фоновая задача первого старта; API отдаёт частичные данные по мере заполнения.
  На первом деплое разумно дождаться завершения бэкфилла **до публичного запуска**. По
  завершении worker переключается на инкрементальный скан новых блоков.
